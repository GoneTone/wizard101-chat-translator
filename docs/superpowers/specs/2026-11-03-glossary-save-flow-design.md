# 設定視窗的儲存流程：子編輯器即時寫檔、關窗前確認

## 動機

設定視窗底部的〔取消〕〔儲存〕是整個視窗共用的：〔儲存〕寫出全部設定並關窗，〔取消〕丟掉全部改動並關窗。術語表的編輯畫面是分頁內的子畫面，使用者編輯時第一直覺會按底部按鈕，結果整個視窗被關掉；按〔取消〕或 ✕ 還會不提示就丟掉剛打的條目。

服務對話框有自己的〔確定〕，但〔確定〕只改暫存，之後按視窗〔取消〕／✕ 一樣會不見。

## 目標

1. 術語表編輯畫面：底部按鈕列換成「這份術語表」的〔取消〕〔儲存〕。〔儲存〕馬上把**這一份**寫進設定檔並回到清單，視窗不關。
2. 服務對話框：〔確定〕改為〔儲存〕，按下後馬上把**這一筆服務**寫進設定檔。
3. 按 ✕ 或 Alt+F4 關閉設定視窗時，只要有沒存的改動就跳確認對話框。

## 非目標

- 清單層的操作（刪除、複製術語表，切換啟用的術語表；刪除服務、設預設、指定用途）維持現狀，等視窗〔儲存〕才寫檔。
- 首次設定精靈不動。
- 視窗的〔取消〕按鈕不加確認：它本身就是明確的放棄動作。

## 反目標（做到了也算失敗）

- 子編輯器存檔時，順便把清單層還沒存的改動寫出去。例如在清單刪了 A，再編輯 B 並按儲存，A 的刪除被一起寫進檔案。
- 在編輯畫面切到別的分頁再按視窗〔儲存〕，結果把還沒按「這份的儲存」的內容寫出去。
- 子編輯器存檔時，把 overlay 預覽中的透明度、介面語言等其他設定重設或寫出去。

## 做法比較

- **A. 底部按鈕列隨畫面切換（採用）**：在編輯畫面時，底部是這份術語表的〔取消〕〔儲存〕，回到清單後恢復成視窗按鈕。使用者照直覺按就是對的，新增的介面最少。代價是同一位置在不同畫面意思不同，因此按鈕列左側加一行「正在編輯「○○」」。
- B. 編輯畫面自己加一排按鈕，底部不動：改動小，但使用者照直覺按底部的問題依舊存在。
- C. 編輯畫面改成大對話框：和服務對話框一致，但條目多時太擠，`LazyRows` 的分段載入要重做，成本最高。

## 決定的行為

### 術語表編輯畫面

- 進入編輯（〔編輯〕、新增空白、從檔案新增）時，編輯的是一份**獨立副本**，不是 `GlossaryDraft` 裡的那份。視窗的 `collect()` 不會看到副本。
- 左上的「← 返回清單」拿掉。
- 只要術語表分頁停在編輯畫面，底部按鈕列就換成：
  - 左側一行「正在編輯「名稱」」（名稱空白時改用預設稱呼）。若有擋下儲存的原因，改顯示原因。
  - 右側〔取消〕〔儲存〕。
  - 切到其他分頁時，底部恢復視窗按鈕；切回術語表分頁時，編輯畫面與副本仍在。
  - 這時若按視窗〔儲存〕，而副本有沒存的編輯（判斷同〈關窗確認〉），就**擋下儲存**，不寫檔、不關窗。擋下的原因列在現有的錯誤提示裡：「術語表「{name}」還有沒儲存的編輯」，跟其他擋儲存的原因一起顯示。副本沒有改動時，就照常儲存並關窗，副本直接丟掉。
- 〔儲存〕：只檢查這一份。檢查項目沿用 `GlossaryDraft::errors()` 的規則：名稱空白、來源重複、條目只填一側。
  - 沒過：在底部列出原因，不寫檔、不離開。
  - 過了：副本寫回 `GlossaryDraft`（同 id 取代，新的加在最後），並把這一份寫進設定檔（見〈即時寫檔〉），然後回到清單。
- 〔取消〕：丟掉副本並回到清單，不確認。新增後從沒存過的那份，草稿裡本來就沒有，取消就等於不新增。
- 編輯畫面內的「匯入合併」改的是副本，跟著〔儲存〕／〔取消〕走。
- 新增流程中，「從檔案新增」解析成功後才開編輯畫面，這點維持現狀。

### 服務對話框

- 〔確定〕改為〔儲存〕。先跑現有的欄位檢查，再拿合併後要寫出的鍵（基準換掉這一筆）跑視窗層的 `service_errors` 與 `local_errors`，例如各用途的本地模型加總塞不進記憶體。任一項沒過，就在對話框底部列出原因，不寫檔、不關對話框。都過了，就照現在的方式併回 `ServiceDraft`，並把這一筆寫進設定檔。（我的判斷：視窗〔儲存〕會擋的，即時存檔也要擋，否則寫出的設定會馬上生效。）
- 若這是設定檔裡的第一筆服務，`apply_dialog_result` 會讓它接手預設；這個情況下 `default_service` 也一起寫進檔案，否則寫進去的服務會沒有預設可用。

### 即時寫檔

- 視窗另外記一份「已存檔的基準」：開窗時從 `cfg` 取得 `glossaries`、`active_glossary`、`services`、`default_service`、`service_slots` 這幾個鍵。
- 子編輯器存檔時，以基準為底，只換掉（或新增）那一筆，算出這幾個鍵的新值。寫出前的整理沿用 `GlossaryDraft::write_into` 的規則：去頭尾空白、去重、去掉跟內建相同的條目、撞名補序號，撞名只跟基準比。接著更新基準，再送給 App。
- 新增一個 `SettingsAction`，例如 `Commit(Config)`，只帶上述的鍵。App 收到後走後端的 `app_main::apply_settings`（併入共用設定、存檔、翻譯端與本地模型跟上），**視窗不關**，也**不呼叫** overlay 端的 `App::apply_settings`。overlay 端會用部分設定的預設值，把預覽中的透明度等蓋掉。
- 存檔失敗沿用現有的 `ConfigSaveFailed` 提示。

### 關窗確認

- 「有沒存的改動」的判斷，符合任一項就算：
  - 視窗 `collect()` 的結果與基準不同。
  - 術語表副本與進入編輯時不同。新增後從沒存過的那份（空白或從檔案新增）一律算。
  - 服務對話框開著，且表單內容與開啟時不同。表單要記下開啟時的內容。
  - （以上兩項是我的判斷，延續「有沒存的就問」：剛匯入、還沒存的術語表，以及打到一半的服務，都屬於會不見的東西。）
  - 基準在開窗時取 `collect()` 的初值；每次即時寫檔與視窗〔儲存〕時跟著更新。
  - 介面語言的預覽算改動，透明度的預覽也是：`collect()` 本來就涵蓋這兩項。
- ✕／Alt+F4（`settings_host.rs` 裡的 `closing`）：
  - 沒有改動：照現在直接取消並關閉。
  - 有改動：不關，跳確認對話框，問要不要放棄沒存的變更。按〔放棄〕就走現有的 `cancel()` 並關閉；按〔取消〕或 Esc 就留在視窗。
  - 對話框開著時又按一次 ✕，維持對話框，不關窗。
- 視窗〔取消〕按鈕：維持不確認，直接取消。只有術語表編輯畫面時，底部才不會出現這顆按鈕。
- 確認對話框沿用 `dialog::confirm`，確定鈕用 `danger_button`，文字為〔放棄〕。

### 文案與 log

- 新增的字串：「正在編輯「{name}」」、關窗確認的問句、〔放棄〕、擋儲存的「術語表「{name}」還有沒儲存的編輯」（名稱空白時用第幾份稱呼，比照 `error.glossary_*_unnamed`）。〔確定〕改〔儲存〕可直接用現有的 `button.save`。拿掉「返回清單」後，`glossary.back_to_list` 如果沒有別處在用就刪掉。
- 新字串要補到每個有翻譯的語系檔（`src/i18n/locales/`）；問句結尾的標點在各語言要一致。
- log 一律英文、帶 id：`[settings] glossary {id} committed`、`[settings] service {id} committed`、`[settings] close blocked: unsaved changes`、放棄或留下的結果。

## 限制

- 不能把 API 金鑰寫進 log。
- 搶焦點、開視窗的動作不能進測試。純邏輯放在可單獨測的函式裡，例如基準的合併、改動的判斷、按鈕列在哪種模式。
- 測試一律經 key 取字串，不綁翻譯後的句子。

## 留給實作者

- `Commit` 的確切命名，以及 App 端如何拿到 `on_save` 又不關窗。
- 副本放在 `GlossaryEditor` 裡，還是放在 `Screen::Edit` 旁邊。
- 底部按鈕列切換的實作方式：由 `GlossaryPane` 回報「在編輯中」，視窗據此換掉 `footer`。
- 即時寫檔會連帶讓 `app_main::apply_settings` 重新註冊熱鍵。如果熱鍵正在錄製中，要確認不會互相干擾；必要時把熱鍵重新註冊從 commit 路徑拆出去。

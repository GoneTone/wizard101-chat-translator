# Wizard101 聊天翻譯助手：翻譯視窗訊息清單改為每分頁一個畫布設計

日期：2026-10-14
狀態：設計完成，待實作。

## 目標

翻譯視窗切換分頁時不再凍結。PR #40 加入分頁同步後，切換分頁會把該分頁的訊息列全部銷毀再重建；
每則訊息是兩個原生 `tk.Canvas`（原文行、譯文行），每行 9 個文字物件（8 個描邊副本＋本色）。

實測（翻譯視窗停在螢幕外，計時含排版與繪製）：

| 每分頁訊息數 | 現況切換凍結 |
|---|---|
| 50 | 0.32 秒 |
| 200（預設上限） | 1.3 秒 |
| 500 | 3.6 秒 |
| 1000（設定上限） | 8.0 秒 |

本案把訊息清單改成：**每個（客戶端, 分頁）一個畫布，訊息文字直接畫成該畫布上的文字物件**，切分頁只是
換掉顯示中的那個畫布。原型實測切換 1–2 ms、與訊息數無關，新增一則從約 5 ms 降到 0.5 ms。

## 非目標

- **外觀與操作完全不變**（使用者確認）：不調整字型、顏色、間距、描邊，不新增任何操作。
- 不改分頁同步、收訊、翻譯、橫幅、泡泡、標題列等其他部分的行為。
- 不做虛擬化（只畫可見範圍）：每分頁一個畫布已讓切換與訊息數無關，Tk 畫布本身只重繪可見區域。

## 反目標

- 任何肉眼可見的外觀差異（描邊、原文調暗、譯文遊戲色、佔位色、錯誤色、換行、列距）。
- 框選複製、捲動跟隨、捲動錨點的任何既有行為改變；既有測試只能改「取得畫面元件的方式」，不能放寬斷言。

## 評估過的做法

| 做法 | 200 則切換 | 1000 則切換 | 新增一則 |
|---|---|---|---|
| 現況：切換時銷毀重建每行畫布 | 1.3 秒 | 8.0 秒 | 約 5 ms |
| 保留各分頁的畫面元件、只切換顯示的 frame | 0.28 秒（最久 0.77） | 1.7 秒（最久 4.0） | 約 5 ms |
| 全部文字畫在單一畫布、切換時隱藏／顯示 | 0.15 秒 | 0.65 秒 | 0.5 ms |
| **每分頁一個畫布、文字直接畫，切換時換畫布** | **1–2 ms** | **2 ms** | **0.5 ms** |

瓶頸是原生視窗數量：每行一個 `tk.Canvas`，顯示、隱藏、重建數百個原生視窗的成本都與數量成正比。只有最後
一種讓每個分頁只對應一個原生視窗。

## 決策摘要

| 決策 | 選擇 | 來源 |
|---|---|---|
| 架構 | 每個（客戶端, 分頁）一個 `tk.Canvas`，訊息為該畫布上的文字物件 | 評估結果（我的判斷） |
| 外觀與操作 | 完全不變 | 使用者決定 |
| 效能防退化 | 切分頁與新增訊息的耗時寫成自動測試，超過門檻即失敗 | 使用者決定 |
| 切換的門檻 | 兩個分頁各 1000 則，切換中位數 ≤ 100 ms | 原型 1–2 ms 的約 50 倍餘裕，避免 CI 機器較慢而誤報（我的判斷） |
| 縮放視窗時隱藏中的分頁 | 不立即重排，切過去時才補做 | 我的判斷 |
| 效能測試的執行時機 | 放在預設的 `uv run pytest` 裡（本機 4 個 worker 平行、CI 序列都跑），同一檔的測試用 `xdist_group` 排在同一個 worker，避免彼此搶 CPU | 「提交前全綠」要能擋下退化；不改 9 處開發指令（我的判斷） |
| 新增一則的門檻 | 平均 ≤ 3 ms／則（原型 0.5 ms，現況約 5 ms） | 留 6 倍餘裕給平行執行的干擾，又能擋下退回「每行一個原生視窗」的畫法（我的判斷） |

## 元件設計

### 1. `src/ui/message_list.py`（重寫內部，公開介面不變）

**公開介面維持**：`MessageList(parent, selection, *, max_messages, fade_seconds, wrap, bottom_inset,
bind_line, on_wrap_change)`、`frame`、`wrap`、`shown_key`、`add_message(key, ...)`、`update_message`、
`show(key)`、`set_limits`、`prune`、`on_wheel`、`note_scroll`、`scroll_by`、`viewport`、
`refresh_scroll`、`scroll_debug`、`set_placeholder`、`refresh_fonts`、`visible_messages`、
`placeholder_visible`。`bind_line` 的意義改成「每個新建的分頁畫布建好時呼叫一次」，參數仍是一個
`tk.Canvas`（見第 3 節）。

**畫布**：
- 每個 key 一個 `tk.Canvas`（`bg=BG`、無邊框），建在原本放內層 frame 的位置，同一時間只 pack 顯示中的那個。
- 單一捲軸：`show()` 時把捲軸的 command 與顯示中畫布的 `yscrollcommand` 接到新畫布，舊畫布斷開。
- 滾輪：每個畫布都綁 `<Enter>`／`<Leave>` 轉發到 `on_wheel`，與現況相同。

**訊息排版**：
- 一則訊息＝原文行＋譯文行，每行仍是 8 個描邊副本＋1 個本色文字物件，字型、顏色、`TEXT_ORIGIN`
  偏移、換行寬度、列距（`pady=2` 對應的 2 px 上下間距）與現況逐像素相同。
- 每行的文字物件共用一個行專屬 tag，本色物件另帶可辨識本色的 tag（`selection` 要用，見第 2 節）；
  移動與刪除整則時直接用物件 id（`line_items`）；訊息身分只靠記錄裡的 tag 字串當鍵，不另在畫布物件上掛訊息 tag。
- 新訊息排在該畫布目前內容的下方；`scrollregion` 取該畫布的內容範圍。
- 刪除最舊訊息（上限、淡出）直接刪除物件，不必把其餘內容往上搬（`scrollregion` 會跟著縮）。
- `update_message` 改了譯文後若行高改變，把該則以下的訊息整體往下或往上移動差值。

**換行寬度**：
- 畫布寬度改變時，顯示中的畫布以單一 tag 一次更新所有文字物件的寬度並重新排版。
- 隱藏中的畫布記為「換行寬度過期」，`show()` 切到它時才補做。

**顯示中的畫布與既有行為的對應**：
- 跟隨底部、捲動錨點（`_view_anchor`／`_restore_anchor`）改以「最新一則的畫布座標」計算，語意不變。
- `show(key)`：清除選取、換 pack 的畫布、必要時補做換行、回到跟隨底部、更新空狀態提示、記 log
  `[ui] view switched (slot=…, tab=…, messages=…)`；切到同一個 key 不做任何事。
- 訊息上限、淡出、`update_message` 對隱藏中的畫布照常生效。

### 2. `src/ui/selection.py`（以「行」為單位的抽象改成畫布上的文字物件）

**公開介面維持**：`Selection()`、`active`、`dragging`、`register(row, lines)`、`forget(row)`、
`holds(row)`、`span()`、`text()`、`begin`、`extend`、`finish`、`clear`、`redraw`，以及模組函式
`line_text`、`line_font`、`caret_at`、`visual_lines`、`highlight_rects`、`selected_text`。

- 「一行」從「一個畫布 widget」改成「畫布＋該行本色文字物件」的行把手（`row` 也改成可雜湊的訊息識別，
  例如訊息 tag 或記錄本身，由實作決定）。上述模組函式改為吃行把手；`selected_text` 不變。
- 命中測試、夾取、反白都改用畫布座標（螢幕座標扣掉畫布的 root 位置再加上捲動偏移），反白矩形畫在同一個
  畫布上、壓在該行文字之下（同現況 `tag_lower("sel", "txt")` 的效果）。
- 切換分頁時選取清除，`Selection` 只登記顯示中畫布的訊息；隱藏畫布的訊息登記由 `MessageList` 保存，
  `show()` 時整份換入（不得逐筆 `forget`／`register`，那會是 O(n²)）。
- 「點在行的右側很遠處不算命中」等既有判定照舊（以文字物件的 bbox 取代畫布 widget 的範圍時，命中範圍
  與現況一致：現況的行畫布寬度鋪滿訊息區，水平命中範圍是整個訊息區寬）。

### 3. `src/ui/overlay.py`

- `_bind_line` 改為綁在每個分頁畫布上（滑鼠按下、拖曳、放開、右鍵），一個畫布綁一次；事件處理仍一律用
  螢幕座標，透明背景區的點擊照舊落到 backdrop。
- 其餘呼叫 `self._list.*` 的地方不變。

## 測試

### 既有測試
- `tests/test_selection.py`、`tests/test_overlay.py` 的行為斷言全部保留；只改取得行／列的方式（例如原本
  拿 `entry.row.winfo_children()` 的地方改用新的行把手）。不得刪除或放寬斷言。
- 唯一例外：`test_expand_realigns_the_message_container` 斷言的是內嵌 frame 與捲動位置對齊，守的是
  `refresh_scroll` 裡 `coords(self._inner_id, 0, 0)` 這個補丁；新設計沒有內嵌 frame，補丁與這個斷言一起移除。
  改寫成它要守的使用者可見結果：泡泡期間收到的訊息，展開後最新一則完整落在視口內（我的判斷）。

### 新增
- **外觀不變**：對同一則訊息，新舊畫法的文字物件屬性（文字、字型、顏色、描邊偏移、換行寬度）一致；列距與
  行高與現況一致（可用固定字型量測 bbox 比對）。
- **效能測試** `tests/test_overlay_perf.py`：
  - 兩個分頁各 1000 則，切換 5 次的中位數 ≤ 100 ms（含 `update_idletasks`）。
  - 連續新增 1000 則的平均 ≤ 3 ms／則。
  - 兩者都用與正式路徑相同的 `OverlayWindow`（停在螢幕外），不 mock 畫布。
  - 同檔測試以 `xdist_group` 排在同一個 worker；放在預設的 `uv run pytest` 裡跑。

**原型數字涵蓋的範圍**：原型（`.superpowers/sdd/overlay-canvas-prototypes/`，git 忽略）量的是直接在畫布上
建文字物件與切換 pack，**沒有**走 `OverlayWindow.add_message` 每則都會做的 `refresh_scroll`
（`update_idletasks`＋`yview_moveto`），切換也不含「在新寬度下重排隱藏分頁」。實作第一步要先用正式路徑量；
若新增一則超過門檻，可把同一輪事件裡多次的捲動更新合併成一次（例如排到 idle 才做），前提是跟隨底部與錨點
的既有測試照樣通過。切到「換行寬度過期」的分頁時的重排不計入切換門檻，另以「重排 1000 則與 250 則的耗時比 ≤ 7（線性約 4、平方約 16），且 1000 則 ≤ 10 秒」把關；絕對時間門檻受機器與平行 worker 影響，改以 250 與 1000 則的耗時比值守住「與訊息數成線性」。Tk 每個文字物件換寬度至少重排一次版，8 方向描邊屬外觀不可減，所以不設嚴格的絕對上限。
- 隱藏中分頁的換行過期補做、`update_message` 改變行高後下方訊息位移、刪除最舊訊息後 `scrollregion` 正確。

## 實機驗收

開著遊戲跑 exe：
1. 外觀與 PR #40 版本並排比對無差異（描邊、顏色、佔位、錯誤、換行、列距）。
2. 框選：單行、跨行、跨訊息、拖出上下緣自動捲動、右鍵複製、Ctrl+C。
3. 捲動：新訊息跟到底、往上捲不被拉走、縮放視窗後換行正確；縮成泡泡期間收到訊息，展開後看得到最後幾則。
4. 分頁累積上百則後來回切換無可感受延遲。

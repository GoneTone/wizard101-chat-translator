# hook 跟著遊戲改版自己調整

## 目的

遊戲在 11/12 和 11/17 兩次重新編譯 `WizardGraphicalClient.exe`。新版 exe 內的版本字串是 `W.1.620.01`，連結時間為 2026-11-17。兩次重編後，三個 hook 的 pattern 都全部失效，收訊整個掛不上。

逐一比對兩個版本，變的都是同一類東西：暫存器重新分配、堆疊框大小重算、函式開頭的寫法。結構偏移和程式邏輯都沒有變。

這次改成**每次掛入時看當下的 exe 長什麼樣再組 stub**，而不是把暫存器和位移寫死。這樣同類改版就不必再重修、重新發版。

## 目標／非目標／反目標

- **目標**
  - 新版掛得上。
  - 以後遇到「只換暫存器、堆疊大小、開頭寫法」的改版，不改程式碼也掛得上。
  - 不再需要 autobot 函式。
- **非目標**
  - 指令形狀或結構偏移改變時，仍要人工更新。
  - 同時支援舊版。舊版客戶端進不了遊戲。
  - 發版。由使用者自己做。
- **反目標**
  - pattern 放寬後比對到錯的地方，或 stub 讀錯暫存器，讓遊戲當掉。
  - 有任何一項不確定時，寧可掛不上（顯示不相容橫幅），也不要硬掛。

## 新版實況（靜態分析）

| hook | 新版位置 | 變了 | 沒變 |
|---|---|---|---|
| autobot cave | `0x1417eb460`（4188 bytes） | 整個開頭 | 函式內 `cmp byte [rax+0x21DCE],0` |
| AddLine | `0x140758cf0` | 開頭改成 `mov [rsp+20],rbx` 加 7 個 push；`lea rbp,[rsp-120]`（原本是 `-130`）；開頭後面的指令順序不同 | rcx＝this、rdx＝wstring、r8d＝分頁；`cmp r8d,5; jl`；`[rcx+0x848]` |
| root window | `0x14189400b` | 暫存器 r15 換回 r13；後面接的是 `test bl,bl` | `mov rcx,[reg+D8]; mov rax,[rcx]; mov rdx,[reg+C8]; call [rax+70]` |

## 方案

1. **執行期自己跟著變（採用）**
   - cave 改成自己配置記憶體，刪掉 autobot pattern。
   - root window 和 AddLine 的 pattern 只放寬暫存器、位移、開頭這幾處。stub 用的暫存器和偏移，從比對到的位元組推導出來。
   - 好處：同類改版不必重修，也不必重新發版。
   - 代價：中型改動，放寬後的 pattern 要靠多道檢查擋住誤中。
2. **開發端改版檢查工具**：寫一支腳本讀新版 exe，找出三處並產出新 pattern。只省人工反組譯的時間，使用者仍要等新版，所以不採用。
3. **照 11/12 只換 pattern**：兩種成本都沒有降低，所以不採用。

選方案 1 的理由：兩次改版的變化都落在「推導得出來」的範圍內。推導只在掛入當下做一次，掛上之後每則訊息跑的機器碼和現在一樣。

## 設計

### 1. stub 區改為自配記憶體（取代 autobot cave）

- **配置**：在遊戲模組附近配置一塊可執行記憶體，大小一頁。`E9 rel32` 的跳轉要求它離每個跳轉點都在 ±2 GB 內。
  - `ProcessMemory` 新增一個「在指定範圍內配置」的方法。用 `VirtualQueryEx` 找空閒區段，再以 64 KB 對齊呼叫 `VirtualAllocEx`，指定位址、`MEM_RESERVE | MEM_COMMIT`、`PAGE_EXECUTE_READWRITE`。
  - 範圍內找不到空位，就當作掛入失敗並寫 log，不改寫遊戲任何位元組。這不算版本不符，走一般失敗的路徑和既有的 log 去重。
  - 先完成三個 pattern 的掃描與檢查，再配置與寫入。這樣版本不符時，完全不會動到遊戲。
- **切 stub**：照舊依序切出各 stub。超出這塊大小時仍回 `CaveFull`，錯誤訊息拿掉 autobot 字樣。
- **解除**：照舊依掛入順序寫回各跳轉點，等 `STUB_EXIT_WAIT`，然後釋放 export，最後釋放 stub 區。
  - 不再有「cave 原本的位元組」要寫回。
  - 遊戲已經關掉時，照舊直接略過。
- **hookstate**
  - 還原清單只剩各跳轉點的原碼，不再有 cave 那一筆。
  - `repair` 不再把最後一筆當成 cave 特別處理：全部直接寫回，不必等待。
  - 當掉時遺留的 stub 區不釋放。它很小，留著也確保還停在裡面的執行緒不會出事。
  - 檔案格式不變。v1.5.0 寫下的舊狀態檔對應的是舊版遊戲程序，程序結束後會被 `sweep` 清掉，不必相容。
- **移除的東西**：`AUTOBOT_PATTERN`、`AUTOBOT_SIZE`、`AutobotCave` 這個名稱與相關測試。新名稱由實作者決定，例如 `StubArena`。

### 2. root window：暫存器從比對結果推導

- **pattern**：把兩條指令裡的基底暫存器改成可比對任一個。
  - REX 為 `48` 或 `49`。
  - ModRM 為 `mod=10`，reg 分別是 rcx／rdx。
  - 其餘位元組照舊寫死：`+D8`、`mov rax,[rcx]`、`+C8`、`call [rax+70]`，以及最後的 `84`。
- **比對後的檢查**（任一項不符就當成「不符合此版」，不寫入遊戲）：
  - 先要求唯一命中，再檢查這一處；檢查不會用來篩掉多餘的命中。
  - 兩條指令的基底暫存器（含 REX.B）必須相同。
  - rm 不可為 100：rsp 和 r12 都會需要 SIB 位元組，形狀就不同了。
  - 基底不可為 rcx（rm=001 且 REX.B=0），因為第一條指令就會把它蓋掉；r9 可以。rax、rdx 無妨，stub 讀 `[基底+D8]` 的時機和原指令一樣。
- **stub**
  - `push rax`
  - `mov rax,[基底+D8]`：依推導出的暫存器組成。
  - `mov [export],rax`
  - `pop rax`
  - 原指令：直接照抄比對到的 7 bytes。
- **log**：掛上時記下推導出的暫存器。

### 3. AddLine：錨在不變的部分、掛點推導

- **掛點**：函式開頭之後的第一條指令 `lea rbp,[rsp-disp32]`（8 bytes，蓋這一條，`noops` 為 3），位移用萬用字元。
- **pattern 由前到後**
  1. 函式開頭只能是兩種指令，其他都不行：
     - 「存暫存器到 `[rsp+小位移]`」，0 次以上；
     - push，1～8 次，含 `41` 和 `40` 前綴。
  2. 掛點那條 `lea`。
  3. 一段有長度上限的任意位元組，接 `cmp <任一 32 位元暫存器>,5; jl`。
  4. 再一段有長度上限的任意位元組，接位移 `0x848`。
  - 掃描器是 `regex::bytes`，可以用重複次數上限和擷取群組取出掛點位置。
- **比對後的檢查**
  - 先要求唯一命中，再檢查這一處。
  - 比對起點必須 16 bytes 對齊（函式開頭）。
- **為什麼參數還在**：pattern 規定開頭只有「存暫存器」和 push，這兩種都不會改 rcx／rdx／r8。所以到掛點時，三個參數一定還是呼叫時的值。
- **stub**
  - 讀回傳位址的偏移，從比對到的 push 次數算出來：`8 × push 數 + 0x38`（0x38 是 stub 自己的 7 個 push）。
    - 回傳位址只寫進記錄，程式沒有拿來做其他事。萬一 push 數算錯，也只會讓這個值錯，讀的仍是有效的堆疊記憶體。
  - 原指令照抄比對到的 8 bytes。
  - 其餘照舊。
- **log**：掛上時記下 push 數、`lea` 的位移和跳轉點。

### 4. 錯誤與橫幅

比對後的檢查不通過，要跟 pattern 掃不到同等對待：
- 判定為「不符合此遊戲版本」，顯示同一個不相容橫幅；
- 接進 `is_pattern_failure`，沿用既有的版本不符重試間隔（`run_loop.rs` 的 `VERSION_MISMATCH_INTERVAL`）；
- log 寫明是哪一項檢查失敗、比對到的位址與位元組。

### 5. 一併更新

- **測試**
  - `tests/common/fake_game`：能放入不同暫存器（r13、r15、rbx 等）、不同 push 數的開頭，並提供「在範圍內配置」的假實作。新的 pattern 含有分支和重複次數，現有的 `pattern_instance` 無法從 pattern 產生命中的位元組，所以命中的位元組要明確放入。
  - `tests/golden/hook_stubs.json`：依新 stub 重新推導。
  - `hooks_golden.rs`、`mem_reader.rs` 等用到 cave 和 autobot 的測試。
  - 新增反例測試：兩條指令基底不同、基底為 rsp／rcx、開頭混入其他指令、比對起點沒對齊、多重命中，都必須掛不上且不寫入。
- **文件**：CLAUDE.md 與 AGENTS.md 的「記憶體掛入須知」逐字同步：拿掉 `AUTOBOT_PATTERN`，說明暫存器與位移現在是自動推導，只有指令形狀或偏移變了才要改 pattern。
- **過時的註解**：例如「wizwalker 原文」、「位元組必須與 wizwalker 寫入的逐一相同」、autobot 字樣。

## 驗證

- **本機**
  - `cargo fmt --check`、`cargo clippy --all-targets -- -D warnings`、`cargo test`（`-j 4`、`--test-threads=4`）。
  - 用 scratchpad 腳本拿新的 regex 掃本機已安裝的新版 exe，確認三處都唯一命中、命中位置與上表相同，推導出的暫存器、push 數也正確。這支腳本不進版控。
- **實機（使用者執行）**
  - 登入進世界內後 `cargo run`。
  - 確認兩個 hook 掛上、收訊正常、分頁名稱讀得到。`+0x7A0`、`LABEL_OFFSET` 和視窗樹偏移這次只做了推斷；讀不到的話，先停下來回報，不要自行猜改偏移。
  - 確認關閉翻譯器時遊戲不會當掉。

## 留給實作者

- 「存暫存器」指令可接受的編碼範圍，以及 AddLine pattern 兩段任意位元組的長度上限。原則是：新版要唯一命中，而且依 11/12 那版的開頭形狀（`40 55 56 57 41 54 …`，`lea rbp,[rsp-130]`）也要比對得到。
- stub 區的型別名稱，以及「在範圍內配置」這個方法的介面與搜尋順序。
- 新的錯誤變體怎麼命名、怎麼接進 `is_pattern_failure`。

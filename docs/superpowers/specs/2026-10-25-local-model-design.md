# 本地模型 —— 設計

## 為什麼

現在要用本機模型翻譯，使用者得自己裝 Ollama、LM Studio 之類的軟體，再用「自訂端點」連過去；不懂技術的玩家多半卡在這一步。這次讓本程式自己下載 llama.cpp 官方編好的執行檔與 Hugging Face 上的 GGUF 模型，在背景跑起來，使用者在設定裡點幾下就能用本機模型翻譯，不必安裝其他軟體。

llama.cpp 與模型都**不包進 exe**（exe 必須維持單一檔案，模型動輒數 GB），而是使用者在設定裡點了才下載。

## 目標

- 新增「本地」服務商，跟現有服務商一樣在翻譯服務清單裡新增、編輯；表單只從已下載的模型挑一個。
- 設定側欄在「翻譯服務」之後新增一頁「本地模型」，由上而下三張卡片（版面經使用者確認）：
  - **llama.cpp 引擎**：狀態、版本（build）與變體選單、更新／安裝所選版本、刪除；下方顯示偵測到的顯示卡、VRAM／RAM 可用量與「重新偵測」。
  - 背景載入中的資料（硬體偵測、版本清單、repo 查詢）一律畫佔位動畫，不先顯示暫時值再改（使用者決定）；硬體偵測中，相容等級與依它挑的量化／推薦也是佔位。精靈的推薦等推薦 repo 全部查完才顯示，全部查詢失敗時顯示原文與〔重試〕。
  - **模型載入**：「啟動時預先載入模型」開關（預設關；說明文字經使用者定稿：「本工具開啟時就在背景預先載入本地服務用到的模型，第一句翻譯不用等待模型載入；關掉的話等第一句翻譯時才會載入模型，會需要等待一點時間。」）、閒置卸載（不卸載／5／15／30 分鐘，預設 15 分鐘）。
  - **已下載模型**：每個模型的大小、相容等級、MTP 開關、刪除；下載中顯示進度與取消，中斷的顯示「繼續下載」；總佔用空間；沒有模型時顯示空白提示。卡片右上角「＋ 下載模型」開啟下載對話框。
- 「下載模型」對話框，兩個分頁：
  - **推薦模型**：內建清單，每列顯示自動挑好的量化版本與相容等級，一鍵下載；「選擇版本」展開量化表（依位元數分列、色點表示等級、MTP 另列）手動挑；已下載的標示出來。
  - **自訂（Hugging Face）**：貼 repo（網址或 `org/repo` 皆可），查詢後列出同樣的量化表，挑好下載。
  - 按下載後對話框關閉，進度出現在「已下載模型」卡片。
- 依使用者硬體判斷每個量化版本的相容等級（三級），類似 Hugging Face 的 Hardware compatibility，但用偵測到的實際可用記憶體（扣掉遊戲正在用的）。
- 支援 MTP 推測解碼（獨立 MTP 檔與內建在主檔兩種形式）。
- 四條翻譯路徑（收訊、發話、系統訊息、框選）都能用本地服務。

## 非目標

- 包進 exe 或隨安裝檔附帶引擎、模型。
- 需要登入或授權同意的 Hugging Face repo（gated／private）；遇到時顯示伺服器原文錯誤即可，不做 token 輸入。
- 翻譯專用模型（Hy-MT2、Index-Translate 等）的專屬提示詞路徑；它們是固定格式訓練、不支援我們的 system prompt 結構，不列入推薦清單（使用者仍可用自訂 repo 下載，品質自負）。
- 同一個 llama-server 載入多個模型（router 模式）、多張顯卡分配、讓使用者調 `-ngl`／`--n-cpu-moe`／context 大小等進階參數。
- GGUF 以外的格式（safetensors、MLX 等）、看圖（mmproj）功能。
- 遠端更新推薦清單（清單寫在程式裡，隨版本發佈）。

## 限制

- exe 維持單一檔案；引擎與模型下載到 `app_dir()` 底下（發行版為 exe 旁、開發時為專案根目錄），分 `llama/`（引擎）與 `models/`（模型）兩個子資料夾。開發時這兩個資料夾要加進 `.gitignore`。
- 推論與遊戲同時搶 GPU／VRAM／RAM；相容判斷必須反映「遊戲開著時」的可用量。
- 新服務商要處理 prompt cache（CLAUDE.md 規則）：llama-server 預設 `cache_prompt` 會重用相同前綴的 KV，等同自動快取，不需要標記；沿用 `[translate] prompt cache:` log —— llama-server 回應的 `timings`／`usage` 若帶快取命中數就記下，沒有就記 n/a。
- 介面新字串要補進每個有翻譯的語系檔（`src/i18n/locales/*.json`）。
- log 一律英文、帶足 context（`[local]` 前綴），不得寫入任何金鑰；下載網址的簽章查詢字串（HF CDN 的 `Policy`／`Signature`）不寫進 log。
- 錯誤訊息只顯示伺服器原文，不加推測（既有原則）。
- 推薦清單裡的模型要語言範圍廣（目標語言是使用者自訂）、授權寬鬆、會照 system prompt 走。

## 做法（考慮過的）

本程式怎麼驅動 llama.cpp：

- **A. 背景啟動 `llama-server.exe` 子程序（採用）**：本程式下載、啟動、關閉 llama-server，翻譯經本機埠走現有的 `OpenAiCompatClient`。翻譯層幾乎不用新寫；prompt 快取、MTP、MoE 專家放 RAM、閒置卸載、記憶體自動調配都是 llama-server 現成功能；llama.cpp 當掉只掉子程序，不會拖垮 overlay 與遊戲 hook；更新就是換一包 zip。代價是要管子程序生命週期、挑埠、等載入完成、處理防毒誤擋。
- **B. 下載 llama.cpp 的 DLL，程式內呼叫 C API**：沒有子程序與埠，但 llama.cpp 的 C API 幾乎每版都變，「使用者自行更新引擎」就不成立；聊天模板、取樣、MTP、前綴快取都得自己重做；DLL 一當整個程式就倒。
- **C. 純 Rust 引擎（candle、mistral.rs）**：不符合「下載 llama.cpp」的需求，新架構（Gemma 4、Qwen3.8）支援通常落後 llama.cpp。

使用者選 A。

## 已決定的設計

### 服務商與翻譯路徑

- `PROVIDERS` 新增 `local`：欄位只有模型（已下載模型的識別）與思考開關（預設關）；不需要 API 金鑰、base_url、effort。驗證規則：模型必須是已下載的模型，沒選就擋儲存。
- `build_client` 對 `local` 建一個 `OpenAiCompatClient`，base_url 指向本程式啟動的 llama-server（`http://127.0.0.1:<port>`）。思考關閉沿用現有的 `chat_template_kwargs: {"enable_thinking": false}` 分支（Qwen3.5 預設開思考）。
- 本機連線已有 `bypass_proxy_for_loopback`。

### 引擎（llama.cpp）

- 來源：GitHub `ggml-org/llama.cpp` releases 的 Windows 資產，命名如 `llama-b11871-bin-win-vulkan-x64.zip`（約 37 MB）、`llama-b11871-bin-win-cuda-13.4-x64.zip`（約 160 MB，另需 `cudart-llama-bin-win-cuda-13.4-x64.zip` 約 424 MB）、`llama-b11871-bin-win-cpu-x64.zip`（約 24 MB）。
- 依硬體自動挑版本（使用者決定 NVIDIA 自動用 CUDA）：NVIDIA 獨顯 → 卡與驅動撐得起的最新 CUDA 版（CUDA 12.x 要驅動 528.33 以上；13.x 要 580 以上，且只支援 Turing 以後，以 PCI device ID ≥ 0x1E00 判斷；驅動版本從 DX12 adapter 讀；讀不到或太舊就用 Vulkan，連同 cudart 約 600 MB）；其他獨立／內建 GPU → Vulkan 版（檔案小）；沒有可用 GPU → CPU 版。都可以在管理頁手動切換。下載前認 GPU 廠牌可以用已有的 `wgpu` 列舉 adapter（`vendor` 與 `device_type`），不需新增相依。
- 版本：追 GitHub 上最新的 `bNNNNN` build（穩定版 tag 如 `v0.7.0` 沒有附 Windows 執行檔，編好的檔案只在預發佈的 build 裡）。首次下載預設取當下最新的 build；之後管理頁顯示目前 build 與最新 build，有新版就提示，由使用者自己點更新，不自動換。（使用者決定）
- **使用者可以自選要下載哪個 build**（使用者決定）：管理頁列出近期的 build（GitHub releases API，只列有對應 Windows 資產的；列多少筆由實作決定），選一個安裝，可以往前退到舊 build。變體（Vulkan／CUDA／CPU）是另一個選項，預設依硬體自動挑，也可以手動改。
- **最低支援版本**：程式內常數 `MIN_BUILD = b11871`（2026-10-25 的最新 build），比它舊的 build 不列出、不可安裝。本程式依賴的參數（`--sleep-idle-seconds`、`--spec-type draft-mtp`、預設開啟的 `--fit`）與推薦模型的架構都需要近期版本；之後依賴更新的參數或模型時一併調高。llama.cpp 日後改參數名稱造成新版啟動失敗，由下一條的自動退回與「顯示 llama.cpp 原文錯誤（exit code 與最後幾行輸出）」處理。（我的決定，回應版本相容的提醒）
- 更新時保留舊版資料夾，新版第一次成功啟動（`/health` 就緒）後才刪掉舊版；新版啟動失敗就自動退回舊版並記 log，避免使用者卡在一個壞掉的 build。（我的決定）
- 子程序生命週期：
  - 以 Windows Job Object（`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`）綁住，本程式結束或當掉時系統一併結束子程序。
  - 不開主控台視窗（`CREATE_NO_WINDOW`）；stdout／stderr 轉進 `app.log`（`[local]` 前綴，可節流）。
  - 埠：啟動前向系統要一個空的本機埠，以 `--host 127.0.0.1 --port <port>` 明確指定（新版預設埠已改成 9931，不要依賴預設值）。
  - 就緒判定：輪詢 `GET /health` 直到 200；逾時或程序提前結束 → 記 log（帶 exit code 與最後幾行輸出）並在 UI 顯示錯誤。
  - 子程序意外結束 → 記 log，下一次翻譯請求時重新啟動一次；連續失敗就停在錯誤狀態，不無限重啟。
- 啟動參數由本程式組：`-m <模型>`、`--host`／`--port`、`--sleep-idle-seconds <秒>`（使用者選「不卸載」時不帶）、MTP 相關（見下）。其餘交給 `--fit`（預設開，依實際可用記憶體自動決定 GPU 層數與 MoE 專家擺放）。

### 載入與卸載時機

- 「啟動時預先載入模型」開關（預設關，放在「本地模型」頁的「模型載入」卡片，與閒置卸載同一張；使用者決定）：開著時本程式啟動就在背景啟動 llama-server 並載入本地服務用到的模型，第一句不用等；關掉則等第一句翻譯時才啟動。
- 閒置卸載交給 llama-server 的 `--sleep-idle-seconds`：卸載後下一個請求自動重新載入。重新載入期間 overlay 橫幅顯示「載入模型中」之類的狀態（可先查 `GET /props` 的 `is_sleeping`，或請求送出後一段時間沒回應再顯示，由實作挑），不要看起來像當掉。
- 閒置卸載是全域設定，放在「本地模型」頁，不放在服務表單。

### 多個用途使用本地模型

收訊、發話、框選三個用途（`ServiceSlot`）各自指定服務：

- 用到同一個本地模型的用途共用一個 llama-server。
- 用到不同本地模型時，**每個模型各跑一個 llama-server**（各自的埠、各自閒置卸載），前提是硬體放得下：這幾個模型的所需記憶體加總（同一套相容判斷）不超過 VRAM＋RAM 可用量才允許；超過就擋住儲存，紅字說明「這幾個模型同時載入放不下」並列出各自所需量。加總只到「會慢」時允許但標示。（使用者要求依硬體判斷是否允許；判斷規則是我的提議）
- 子程序依序啟動，每個都等 `/health` 就緒後才啟動下一個，讓 `--fit` 看到前一個已佔掉的記憶體。
- 沒有任何用途引用某個模型 → 結束它的子程序；全部用途都換成雲端 → 全部結束。
- 設定視窗的測試翻譯：表單選的模型若還沒在跑，就臨時啟動它來測（不受上面的加總檢查限制），關掉設定視窗或儲存後依實際設定收掉多餘的子程序。（我的決定）

### 模型來源（Hugging Face）

- 輸入接受 `https://huggingface.co/<org>/<repo>`（含 `/tree/main` 等尾巴）與 `<org>/<repo>` 兩種，解析成同一個 repo。
- 檔案清單：`GET https://huggingface.co/api/models/<repo>/tree/main?recursive=true`（必須遞迴 —— MTP 與大模型分檔常放在子資料夾）；每個檔有大小與 LFS sha256。
- 下載：`https://huggingface.co/<repo>/resolve/main/<path>`（302 轉到 CDN，支援 `Range`）。要能顯示進度、取消、中斷後續傳；下載完驗 sha256；下載前檢查磁碟剩餘空間。
- 檔案分類：
  - 主模型：其餘的 `.gguf`。
  - 排除：檔名含 `mmproj`（前綴或後綴都有，如 `mmproj-F16.gguf`、`gemma-4-26B-it-mmproj.gguf`）。
  - MTP 檔：檔名以 `mtp-` 開頭（可能在 `MTP/` 子資料夾）；另列，不當主模型。
  - 分檔：`-00001-of-0000N` 這類視為同一個選項，大小合併，下載時一起抓。
- 量化名稱從檔名解析，要涵蓋 unsloth 的 `UD-` 前綴與 `IQ*`、`MXFP4_MOE`、`q4_0`（小寫）等寫法；解析不出來就顯示檔名。
- 有的 repo 只有一個量化檔（例如 Google 官方 QAT repo），展開量化表要能處理只有一個選項。
- 本地存放：每個模型一個子資料夾（主檔、分檔、MTP 檔放在一起），並記下來源 repo 與檔名，以便管理頁顯示與刪除。

### 相容判斷

- **可用記憶體**：
  - VRAM：引擎已下載時，用 `llama-server --list-devices` 的輸出（每個裝置的總量與可用量，跟 llama.cpp 實際看到的一致）。引擎未下載時相容等級顯示「未知」，提示先下載引擎。
  - RAM：`GlobalMemoryStatusEx`（`windows-sys` 已啟用的 `Win32_System_SystemInformation`）。
  - 量測當下遊戲若沒開，可用量會偏高；畫面上註明「以目前可用量估算」，不另外猜遊戲佔用。
  - 內顯（共享記憶體，`--list-devices` 會把系統 RAM 報成裝置記憶體）：只算一次、當成 RAM，不跟 RAM 相加；這種機器不會出現「流暢」，放得進 RAM 就標「會慢」。（我的決定）
- **所需記憶體** ≈ 模型檔大小（含分檔）＋ MTP 檔（若有選）＋ 上下文 KV cache ＋ 固定餘裕。KV cache 從 GGUF 檔頭算（`block_count`、`attention.head_count_kv`、`key_length`／`value_length` 等，乘上實際使用的 context 長度）；檔頭以 HTTP `Range` 只讀開頭，不下載整個檔（檔頭含 tokenizer 詞表，可能數 MB，要能分段讀到 tensor 資訊為止）。
- **MoE**：檔頭的 `expert_count` > 0 即為 MoE。MoE 只要 VRAM＋RAM 合計放得下就算可用，因為 `--fit` 會把專家權重放到 RAM、速度仍可接受。
- **MTP**：檔頭最後一個 block 有 `nextn` 張量（`blk.{N-1}.nextn.eh_proj.weight`）表示主檔內建 MTP；llama.cpp 自己也是這樣判斷。
- **三級**：
  - 流暢：全部放得進 VRAM。
  - 會慢：要用到 RAM（一般模型部分放 RAM；MoE 見上則仍算可用但標示）。
  - 放不下：VRAM＋RAM 都不夠。可以下載，但跳警告，不擋。
- 具體門檻與餘裕數字留給實作，用實際機器校準。
- **實測校準（使用者決定：記憶體數字要準，不靠猜）**：模型載入過一次後，改用它實際用掉的量；沒載入過的才用上面的估算，介面標「預估」。
  - 量法：llama-server 就緒當下，VRAM 讀 Windows 效能計數器「GPU Process Memory\Dedicated Usage」（含 CUDA 驅動與 context，llama.cpp 自己印的 buffer 加總會少算），RAM 讀程序的 working set；之後每次重新偵測硬體時對跑著的模型再量一次，同一種載入方式保留最大值（第一次請求後還會長）。不加總 llama.cpp 印的 buffer 行（同一個 context 的 compute buffer 會印兩次）。
  - 是否每層都放 GPU：啟動參數加 `-lv 4`，讀 `load_tensors: offloaded n/m layers to GPU`（主模型與 MTP 草稿各印一次，任一次 n < m 就是部分卸載；`--fit` 試算印的是另一張表，不算）。`--fit` 把張量（例如 MoE 專家）移到系統記憶體時 offloaded 仍是 n/n，但會先印 `cannot meet free memory target`，看到它也算沒全放 GPU。沒看到 offloaded 行（不知道）就不記。
  - 內顯：VRAM 記 0，專用＋共享 GPU 記憶體（「GPU Process Memory\Shared Usage」）與 working set 都算 RAM；獨顯不加共享的，免得與 working set 重複。
  - 記在模型清單（`manifest.json` 的 `measured`：VRAM、RAM、是否全放 GPU、那次有沒有開 MTP），舊清單沒有這欄照樣讀。
  - 判斷：模型的實測與目前的 MTP 開關相同才用 —— 全放 GPU 且 VRAM、RAM 各自放得下為「流暢」；VRAM＋RAM 合計放得下為「會慢」（MoE 為「可用」）；否則「放不下」。MTP 開關不同時退回估算。量的那次沒全放 GPU、而現在可用 VRAM 比它用的多時，看不出現在會不會流暢，也退回估算（標「預估」）；沒比較多則照實測判（不會流暢）。
  - 沒載入過的量化，若同 repo 有量過的其他模型（取權重檔大小最接近的），以它推算：VRAM ＝ 它的實測 VRAM ＋（這個量化的權重 − 它的權重），RAM 與是否全放 GPU 照用，再照上一條判斷；推算的仍標「預估」。
  - 介面：實測的需求顯示「實測：VRAM … GB、RAM … GB」、相容等級不加註；其餘顯示「預估約需 …」，相容等級後加「（預估）」。下載對話框（推薦列、量化表色點與滑過提示）、已下載模型卡、精靈確認卡與多模型儲存檢查共用同一套判斷（`fit::need`／`fit::rate`）。

### 自動挑量化版本

- 預設不依硬體跳選（使用者決定：相容等級已標示，使用者可自行改），與 HF 模型頁「Use this model」的預設一致（使用者決定）：依檔案路徑順序找 `UD-Q4_K*`、`Q4_K_M`、`Q4_K*`。都沒有時固定 4-bit（低於 4-bit 品質通常不好）：最大的 4-bit；沒有 4-bit 挑高於 4-bit 裡最小的，再沒有就挑最大的。相容等級照常標示（會慢、放不下也照實標）。
- repo 有 MTP 檔就一起下載並預設啟用，不看硬體（使用者決定；HF 頁面與 llama.cpp 預設都不帶，使用者選擇預設帶）。挑哪個照 llama.cpp `-hf` 的 `find_best_sibling`：只看主模型資料夾或其上層的 `mtp-` 檔，資料夾最深的優先，再來檔名含 `-{主模型量化}.` 的，再來位元數最接近的，同分取路徑在前的。主模型路徑上沒有 MTP 時（例如 unsloth 把 MTP 獨立放在 `MTP/`，llama.cpp 找不到），改從其他資料夾用同樣的量化與位元數規則挑（使用者決定：有 MTP 就預設帶）；本程式直接把 MTP 檔路徑傳給 llama-server，放哪個資料夾都能用。
- 手動展開時可自己挑主模型量化、要不要 MTP、MTP 哪個量化。

### MTP

- 獨立 MTP 檔：啟動帶 `--spec-type draft-mtp --spec-draft-model <mtp 檔>`。
- 內建在主檔：只帶 `--spec-type draft-mtp`（文件寫「使用主模型自己的 MTP heads」，實作時要實測確認）。
- 管理頁可對已下載模型單獨開關 MTP。啟用 MTP 後 llama-server 啟動失敗 → 自動關掉 MTP 重試一次，並記 log。
- 一句聊天通常只有十幾個 token，MTP 加速有限；框選整頁翻譯才明顯。

### 推薦清單

寫成程式內常數（跟 `PROVIDERS` 同樣做法），每項有 repo 與「精靈可自動挑」旗標（下表高階兩項為否）。新模型要改程式、隨版本發佈。

介面**不顯示**入門／主流／進階／高階這類定位文字（使用者決定），每列只顯示所選量化版本的檔案大小與**預估所需記憶體**（同相容判斷的「所需記憶體」：模型＋MTP＋上下文＋餘裕），再加相容等級。下表的「定位」只是內部挑選與文件說明用。

### 管理頁的操作何時生效（我的決定）

- **檔案類操作立即生效、不進 Save／Cancel 草稿**：下載、刪除、引擎安裝／更新／切換變體。這些是磁碟動作，取消也復原不了。
- **設定類跟著草稿走**：預先載入開關、閒置卸載分鐘數、每個模型的 MTP 開關，按儲存才寫入。
- 下載由長駐的元件負責（不屬於設定視窗），關掉設定視窗仍繼續；重開「本地模型」頁看得到進度。下載中途結束本程式 → 保留未完成的檔案，下次由使用者再點才續傳，不自動開始。
- 刪除已被**已儲存**的本地服務引用的模型 → 跳確認；未儲存草稿裡的引用不特別處理，儲存時的驗證會擋。
- 引擎還沒下載時，點推薦模型的一鍵下載 → 先自動下載引擎（Vulkan／CPU 版只有幾十 MB，CUDA 版約 600 MB），引擎就緒、量到可用記憶體後再自動挑量化版本並下載模型。不另做 `wgpu` 估 VRAM 的第二條路徑。

### 設定與資料

- `config.json` 記：預先載入開關、閒置卸載分鐘數（或不卸載）、引擎版本與變體（Vulkan／CUDA／CPU）、已下載模型清單（來源 repo、檔案、MTP 開關）。本地服務的模型欄位引用已下載模型的識別。
- 刪除模型時，若有本地服務正引用它 → 跳確認，刪除後那些服務標成「模型不存在」，儲存時擋住。

### log 節點

`[local]` 前綴：引擎下載（版本、變體、大小、耗時、失敗的 HTTP 狀態碼）、子程序啟動（參數，不含敏感資料）、就緒耗時、異常結束（exit code、最後幾行輸出）、重啟、睡眠／喚醒、MTP 退回重試；模型下載（repo、檔案、大小、續傳位置、sha256 驗證結果）；相容判斷（偵測到的 VRAM／RAM、每檔所需量與等級）。

### 首次啟動精靈（使用者決定）

- 精靈的服務步驟照常列出「本地」（`provider_cards` 會自動帶出）。
- 選了本地 → 一鍵安裝：依硬體自動挑一個推薦模型（推薦清單中相容等級最好、定位最高的那個，**但只從「精靈可自動挑」的項目裡挑**，高階的 26B／27B 不自動挑 —— 精靈時多半遊戲還沒開、量到的可用量偏高，且首次使用不該等 16 GB 下載），連同引擎一起下載。挑選邏輯與管理頁的自動挑選共用。（我的決定）
- **下載前先確認**：顯示挑中的模型名稱、檔案大小（含引擎）、預估所需記憶體、相容等級，使用者按下載才開始。自動挑的結果可以手動改：「換一個模型或版本」開同一個下載對話框（按鈕改為「選這個」，選完回到確認畫面再按下載），可改選其他推薦模型（含高階）、展開挑量化版本與 MTP，或貼上自訂 Hugging Face repo 挑檔案。（使用者決定）
- 精靈停在這一步顯示引擎與模型的下載進度，**下載完成才能進下一步**（使用者決定）；下載仍由同一個長駐下載元件負責，精靈只是顯示它的進度。
- 等待中可以取消（保留未完成的檔案，之後在管理頁按「繼續下載」），或返回改選雲端服務。
- 下載失敗顯示伺服器原文錯誤，可重試。

## 留給實作的

- 載入中狀態的偵測方式、相容門檻與餘裕數字、context 長度。
- 下載與 GGUF 檔頭解析是否引入現成 crate（先查有沒有可用的 GGUF metadata 解析套件，有就用）。
- 防毒軟體擋下 exe 時的錯誤呈現（只顯示系統錯誤原文）。
- 模組切分：建議新開 `src/local/`（引擎下載與子程序、模型下載、HF API、GGUF 檔頭、相容判斷各自一個檔），UI 在 `src/ui/settings/` 新增管理頁；翻譯層只在 `build_client` 加一個分支。
